1. AI 코어 프로젝트 
1.1 목표 
이번 ‘AI 코어 프로젝트’의 목표는 다음과 같다. 
- 도메인을 스스로 선택하고, 그 도메인에서 근거가 필요한 질문과 데이터 · 
문서 출처를 정의할 수 있다. 
- 선정한 도메인의 데이터를 청킹·임베딩하여 Vector DB에 적재하고, 의미 
유사도 검색으로 활용할 수 있다. 
- LLM 프롬프트로 사용자 질문에서 검색어를 추출하고, 외부 문서 출처(API · 
공공데이터 · PDF)에서 관련 문서를 수집하여 Vector DB에 적재할 수 있다. 
- 검색된 문서를 근거로 답변을 생성하고, 답변의 근거가 된 문서를 사용자에게 
함께 제시할 수 있다. 
- LangGraph를 활용하여 검색(retrieve)과 생성(generate)을 노드로 분리한 RAG 
파이프라인을 구성할 수 있다. 
- 프롬프트의 역할과 출력 형식을 설계하여, LLM 응답을 “하나의 서비스 
기능”으로 연결할 수 있다. 
- 검색·답변 품질에 영향을 주는 요소(청크 크기, Top-k, 검색 다양성)를 
이해하고 조정할 수 있다. 
 
1.2 준비사항 
1) 도메인 선택 조건 
- 도메인은 자유롭게 선택하되, 아래 세 조건을 모두 만족해야 한다. 
◼ 항목 메타데이터 
✓ 서비스가 다룰 항목(예: 영화, 책, 여행, 금융상품 등)마다 이름과 
속성을 가진 데이터를 약 100건 이상 확보한다. 
✓ 1 일차 16시까지 확보하지 못하면 제공 도메인(영화) 팩으로 전환한다. 
◼ 외부 문서 출처 
✓ 항목마다 연결되는 설명 문서를 얻을 수 있어야 한다. (한국어 위키백과 
권장, 공공데이터 · PDF 허용) 
✓ 수집한 데이터와 문서의 출처와 이용 조건을 기록한다. 
◼ 근거가 필요한 질문 
✓ 근거 없이 답하면 틀리거나 위험해지는 질문이 성립하는 주제여야 한다. 
✓ 건강 · 금융처럼 조언이 위험한 도메인은 전문가 조언을 대신하지 
않는다는 안내를 함께 제시한다. 
◼ 제공 도메인 팩 
✓ 영화(예시 구현: Movie Lab)

1.3 작업 순서 
1) 필수 기능, 심화 기능 요구사항을 검토한다. 
2) 도메인을 정하고, 도메인 선택 조건 세 가지를 만족하는지 근거와 함께 확인한다. 
(1일차 16시까지) 
3) 항목 메타데이터 1 건을 어떤 텍스트로 구성할지 정한다. 
4) Vector DB 컬렉션 구조(컬렉션 분리, 메타데이터 필드)를 설계한다. 
5) 프롬프트 세개(검색어 추출/후보 선별/답변 생성)의 역할과 출력 형식을 정한다. 
6) 항목 메타데이터를 임베딩하여 색인한다. 
7) 검색어 추출 프롬프트를 작성한다. 
8) 외부 문서 출처에서 검색하고, 후보 선별 프롬프트로 색인할 문서를 골라 본문과 
원문 출처를 수집한다. 
9) 수집한 문서를 청킹하여 별도의 컬렉션에 색인한다. 
10) 두 컬렉션을 검색하고 결과를 병합/중복 제거하여 근거 목록을 구성한다. 
11) 답변생성 프롬프트를 작성하고, retrieve/generate 두 노드로 LangGraph 를 
구성한다. 
12) 답변에 사용한 근거 문서의 제목과 원문 출처를 화면에 표시한다. 
13) 항목 선택, 질의응답, 조건 기반 탐색, 도메인 특화 기능 화면을 구현한다. 
14) 진행 상태와 비정상 상황(색인 없음, 키 누락, 검색 결과 없음)과 위험 도메인 
안내를 정리한다. 
15) 심화 기능을 선택하여 구현한다. 
16) 요구사항 정의서, RAG 파이프라인 설계문서, 소스코드 등 결과물을 정리하여 
제출한다.

2. 프로젝트 기획 
기획 단계에서는 구현에 들어가기 전에 무엇을 만들지 정한다. 아래의 여섯 가지를 
정하고, 그 결과를 요구사항 정의서와 RAG 파이프라인 설계문서에 담는다.  
2.1 도메인 확정 
- 1 일차 16시까지 도메인을 확정하고, 도메인 선택 조건 세 가지를 모두 
만족하는지 근거와 함께 적는다. 
◼ 항목 메타데이터의 출처와 건수 (약 100건 이상) 
◼ 외부 문서 출처와 이용 조건 
◼ 근거 없이 답하면 틀리거나 위험해지는 질문 3 개 이상 
◼ 건강/금융처럼 판단이 위험한 도메인인지 여부와, 그렇다면 면책 안내 문구 
- 예)영화 964편의 메타데이터와 한국어 위키백과를 사용한다. "인터스텔라의 
블랙홀 묘사는 실제 물리와 얼마나 다른가"처럼 작품 밖 지식이 있어야 답할 수 
있는 질문을 기준으로 삼는다. (영화는 판단이 위험한 도메인이 아니므로 면책 
안내는 두지 않는다.) 
 
2.2 항목 텍스트 설계 
- 항목 1 건을 어떤 속성으로 묶어 하나의 검색 텍스트로 만들지 정한다. 
- 빠진 속성으로는 검색이 걸리지 않으므로, 사용자가 무엇으로 항목을 찾을지를 
먼저 정한다. 
- 예)제목 · 원제 · 개봉연도 · 장르 · 감독 · 출연 · 줄거리를 한 
텍스트로 묶는다. 줄거리를 넣었기 때문에 "우주를 배경으로 한 가족 영화" 
같은 조건 검색이 가능하다. 
 
2.3 컬렉션과 메타데이터 설계 
- 항목 메타데이터와 외부 문서를 각각 어느 컬렉션에 넣을지 정한다. 
- 청크에 함께 저장할 메타데이터 필드와 청크 식별자 규칙을 정한다. 
- 예)영화 메타데이터와 영화 관련 위키문서 두 컬렉션으로 나눈다. 위키 
청크에는 문서 제목, 원문 URL, 문서 ID, 영화 ID, 관련 영화 제목, 검색어, 
수집일을 저장한다. 이 중 영화 ID는 검색 범위를 그 영화로 좁히는 필터로 
쓰이므로, 빠지면 다른 영화의 문서가 근거에 섞인다. 
 
2.4 프롬프트 설계 
- 프롬프트1(검색어 추출): 도메인 전문가 역할로 항목과 질문에서 외부 문서 
검색어를 뽑는다. 결과는 파싱 가능한 형식으로 받는다.

對外秘 
- 프롬프트2(후보 문서 선별): 검색 결과 후보 중 색인할 문서를 고른다. 
- 프롬프트3(답변 생성): 검색된 문서만 사용하고, 근거가 없으면 확인되지 
않는다고 답하도록 제약한다. 
- 검색어 추출, 후보 문서 선별, 답변 생성으로 나눈다. 선별을 따로 둔 이유는 
본문을 받기 전에 버릴 문서를 정해 외부 호출 수를 줄이기 위해서이다. 
 
2.5 검색 설정 설계 
- 근거의 품질에 영향을 주는 값을 정하고, 나중에 바꿔 비교할 수 있게 설정으로 
분리한다. 
- 청크 크기와 중복 길이 
- 검색에서 가져올 근거 수(Top-k) 
- 검색 방식(유사도 검색, 선택 시 MMR) 
- 예) 1,000자 청크, 200자 중복으로 시작한다. 근거 수는 항목 메타데이터 
1 건과 외부 문서 청크 여러 개를 합쳐 정한다. 값은 설정 파일에 두고, 검증 
단계에서 바꿔 근거가 어떻게 달라지는지 확인한다. 
 
2.6 서비스 기능과 화면 설계 
- 도메인 특화 기능 1 개 이상: 무엇을 만들지, 그 기능이 어떤 근거를 쓰는지 
정한다. 
- 조건 기반 항목 탐색: 사용자가 자연어로 조건을 입력하면 어떤 검색과 선별로 
항목을 보여줄지 정한다. 
- 화면에 표시할 안내: 처리 진행 상태, 색인 없음/키 누락/검색 결과 없음 안내, 
해당하면 면책 문구를 정한다. 
- 예) 영화는 관람 가이드(리뷰) 생성과 사실 여부 판정을 특화 기능으로 삼는다. 
둘 다 색인된 문서만 근거로 쓰고 근거를 함께 보여준다. 도서라면 읽기 순서 
안내, 건강이라면 용어 풀이, 금융이라면 상품 조건 비교가 될 수 있다. 
 
2.7 요구사항 
본 프로젝트는 교육생이 선택한 도메인에서 RAG 기반 지식 서비스를 구현한다. 서비스는 
도메인 항목 메타데이터와 외부 문서에서 근거를 검색하여 사용자 질문에 답하고, 
답변의 근거가 된 문서를 함께 제시한다. 도메인은 자유롭게 선택하되, RAG 
파이프라인과 근거 제시는 모든 도메인의 필수 요구사항이다. 영화 도메인의 예시 
구현(Movie Lab)을 시연 자료로 제공한다.

3 장의 요구사항이 실제로 충족되었는지 확인한다. 확인은 실행 결과로 증명하며, 
증명이 필요한 항목은 해당 화면을 캡처하여 첨부한다. 확인 결과는 체크리스트에 통과 
· 실패 · 미확인으로 기록한다. 같은 체크리스트로 직접 점검하고(셀프), 옆 교육생의 
앱도 점검한다(상호). 
4.1 데이터와 색인 확인 (F2001 ~ F2002) 
- 로드한 항목 수와 색인된 청크 수가 일치하는지 확인한다. 
- 색인 작업을 두 번 실행해도 청크 수가 늘지 않는지 확인한다. 
- 항목 1 건의 색인 텍스트를 출력해 의도한 속성이 모두 들어갔는지 확인한다. 
 
4.2 문서 수집과 색인 확인 (F2003 ~ F2005) 
- 하나의 질문에 대해 검색어 추출 프롬프트(프롬프트 1)가 뽑은 검색어 목록을 
확인한다. 
- 후보 중 선별 프롬프트(프롬프트 2)에 따라 실제로 색인된 문서와 버려진 
문서를 구분해 확인한다. 
- 같은 질문을 다시 물었을 때 수집이 다시 일어나지 않는지 확인한다. 
- 선택한 항목 자체를 다룬 문서가 빠지지 않았는지 확인한다. 
- 청크 크기 또는 중복 길이를 설정에서 바꿔 색인했을 때 청크 수가 달라지는지 
확인한다. 
 
4.3 답변과 근거 확인 (F2006 ~ F2008) 
- 검색할 근거 수(Top-k)를 설정에서 바꿨을 때 같은 질문의 근거 목록이 어떻게 
달라지는지 확인한다. 
- LangGraph가 retrieve와 generate 두 노드로 구성되어 있는지 확인한다. 
(그래프 구조 출력 또는 코드 캡처) 
- 답변 본문의 근거 번호와 화면에 표시된 근거 목록이 일치하는지 확인한다. 
- 근거 목록에 항목 메타데이터와 외부 문서가 구분되어 표시되는지 확인한다. 
- 문서에 없는 것을 물었을 때 추측하지 않고 확인되지 않는다고 답하는지 
확인한다. 
- 답변에 인용된 근거가 하나도 없을 때 그 사실이 화면에 안내되는지 확인한다. 
 
4.4 서비스 기능과 화면 확인 (F2009 ~ F2012) 
- 항목을 바꿨을 때 이전 대화가 섞이지 않는지 확인한다. 
- 조건 기반 탐색 결과에 조건과 맞지 않는 항목이 섞이지 않는지 확인한다. 
- 도메인 특화 기능의 결과에도 근거가 함께 제시되는지 확인한다. 
- 문서 수집과 답변 생성 중 진행 상태가 표시되는지 확인한다. 
- 색인이 없는 상태와 API 키가 없는 상태로 실행해 안내가 표시되는지 확인한다.

4.5 심화 기능 확인 (F2013 ~ F2016) 
- 선택한 심화 과제만 확인한다. 
◼ F2013 — 화면이 HTML · CSS · JavaScript로 동작하고 질문 · 답변 · 
근거가 모두 표시되는지 확인한다. 
◼ F2014 — 같은 질문에 유사도 검색과 MMR 검색을 각각 적용해 근거 목록이 
어떻게 달라지는지 확인한다. 
◼ F2015 — 대표 질문에 대한 RAG 사용 전후 답변을 나란히 확보했는지 
확인한다. 
◼ F2016 — 근거 목록에 출처의 종류가 구분되어 표시되는지 확인한다. 
 
4.6 RAG 사용 전후 품질 비교 
- F2015 를 선택한 경우에 확인한다. 
- 대표 질문을 5개 이상 정한다. 근거 없이 답하면 틀리기 쉬운 질문으로 고른다. 
- 같은 질문을 RAG 없이 한 번, 근거를 붙여 한 번 답하게 하고 두 답을 나란히 
기록한다. 
- 사실 정확성, 근거 제시 여부, 모르는 것을 모른다고 답하는지 세 기준으로 
비교한다. 
- 비교 결과를 문서로 작성하여 제출물에 포함한다. 
 
4.7 비기능 요구사항 확인 (NF2001 ~ NF2007) 
- 대표 질문의 전체 처리 시간이 사용에 지장이 없는지 확인한다. (NF2001) 
- 이미 수집한 검색어가 다시 수집되지 않는지 확인한다. (NF2002) 
- 소스코드와 제출물에 API 키가 남아 있지 않은지 확인한다. (NF2003) 
- 화면에 API 키, 프롬프트 전문, 오류 추적 정보가 노출되지 않는지 확인한다. 
(NF2004) 
- 수집 · 색인 · 검색 · 생성 · UI가 모듈로 분리되어 있는지 확인한다. 
(NF2005) 
- 외부 호출의 재시도 · 호출 간격과 출처가 요구하는 식별 정보를 지켰는지 
확인한다. (NF2006) 
- 사용한 데이터와 문서의 출처 · 이용 조건을 기록했는지 확인한다. (NF2007) 
 
4.8 제출 전 점검 목록 
- 필수 기능 F2001 ~ F2012가 모두 동작한다. 
- 선택한 심화 기능이 동작하고, 필수 기능의 결과와 비교되어 있다. 
- 증명을 위한 스크린샷 항목을 모두 첨부했다. 
- 요구사항 정의서 · RAG 파이프라인 설계문서 · 소스코드 · README.md를 모두 
포함했다. 
- 검증 결과(요구사항 대조표, 테스트 결과표, 셀프 · 상호 체크리스트)를 
포함했다.
